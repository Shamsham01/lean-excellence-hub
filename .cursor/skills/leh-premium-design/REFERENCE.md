# LEH Product Design Reference

## Product philosophy

LEH supplies the engine, not the doctrine.

Customers can:

- configure their system;
- use their own terminology;
- create or customise maturity frameworks;
- choose appropriate problem-solving methodologies;
- establish governance appropriate to their organisation.

Built-in LEH standards are accelerators, not mandates.

## Connected product model

Whenever useful, communicate relationships between LEH modules rather than treating modules as isolated apps.

Examples:

Gemba observation
→ Action
→ Problem Solving
→ Project
→ Benefit
→ Learning / Maturity

5S audit
→ Finding
→ Action
→ Closure
→ Sustainment

Suggestion
→ Review
→ Action / Project
→ Benefit
→ Recognition / Learning

Training requirement
→ Scheduled learning
→ Competence
→ Skills
→ Capability
→ Maturity

## Module visual patterns

### Maturity

Prefer:

- maturity matrix
- pillar heatmap
- level bands
- framework status
- assessment progress
- gap-to-target
- trend
- draft / published state

Avoid generic graph cards with arbitrary data.

### Gemba

Prefer:

- walk schedule
- observation
- location / area
- finding
- owner
- action state
- due date
- escalation
- follow-up

### 5S

Prefer:

- planned audits
- adherence
- category scores
- findings
- corrective actions
- ownership
- overdue state
- sustainment

### Suggestions

Prefer:

- idea
- contributor
- submission state
- review
- decision
- feedback
- action/project conversion
- recognition

Do not optimise visually around raw idea count alone.

### Problem Solving

Prefer:

- problem statement
- current condition
- containment
- evidence
- cause analysis
- hypothesis
- verified root cause
- countermeasure
- effectiveness
- sustainment

Remain methodology-neutral unless the context explicitly selects A3, 8D, DMAIC, PDCA or another method.

### Actions

Prefer:

- owner
- due date
- status
- priority
- source
- overdue indicator
- escalation
- closure effectiveness

Action UI should strongly communicate accountability.

### Projects & Benefits

Prefer:

- project objective
- owner/team
- milestones
- progress
- forecast benefit
- realised benefit
- validation
- sustainment

Never display invented financial value as if it were a customer result.

### Training & Skills

Prefer:

- capability matrix
- role requirements
- current competence
- gaps
- planned training
- due dates
- compliance
- future capability demand

### LeanAI

Prefer a contextual assistant model.

Examples:

Context:
Maturity → LEH Operational Excellence Standard → Draft

Context:
Problem Solving → Current case → Root Cause

Context:
Gemba → Current site → Current walk

LeanAI UI should communicate:

Context
+
Assistance
+
Governance

Do not style LeanAI as a standalone generic chat application.

## Marketing conversion

The eventual ideal flow is:

Request demo
→ Qualification
→ Scheduling
→ Confirmation
→ Internal notification / CRM

Until that infrastructure exists:

- stay truthful;
- do not invent an email address;
- do not fake scheduling availability;
- do not fabricate bookings.

Primary commercial CTA should increasingly favour:

Request a demo

Secondary:

Explore the platform

Sign-in remains accessible but is not the primary public marketing conversion.

## Audience hierarchy

LEH serves multiple organisational layers:

Operational Excellence leadership
→ Site leadership
→ Department / Area leadership
→ Frontline teams

Design should support both strategic visibility and frontline action.

## Information density

Strategic pages may emphasise:

- trends
- governance
- performance
- maturity
- capability
- value

Operational pages should emphasise:

- what needs doing
- owner
- status
- due date
- next step

## Product truthfulness

Never invent:

- customer names
- logos
- testimonials
- usage counts
- ROI
- savings
- performance improvements
- awards

Illustrative UI may use neutral example records, but it must not imply those records are real customer performance.

## Final design principle

LEH should not look premium because it has more decoration.

It should look premium because:

- information is intelligently structured;
- workflows feel obvious;
- Operational Excellence concepts feel native;
- interactions are refined;
- visual hierarchy is strong;
- modules feel connected;
- unnecessary friction is removed.
