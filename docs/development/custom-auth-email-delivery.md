# Custom Auth Email Delivery

Lean Excellence Hub routes Supabase Auth transactional email through a Send Email Hook, a Supabase Edge Function, and Resend. This ensures signup confirmation and password recovery links always pass through the application's `/auth/confirm` SSR route so identity enrolment finalisation runs correctly.

## Architecture

```text
Supabase Auth
  -> HTTPS Send Email Hook
  -> Edge Function `send-email`
  -> Resend
```

The Edge Function:

- verifies Standard Webhooks signatures using `SEND_EMAIL_HOOK_SECRET`
- builds branded transactional email content
- generates confirmation links as `${APP_ORIGIN}/auth/confirm?token_hash=...&type=...`
- sends email through Resend using configurable sender values

Signup confirmation **must not** use Supabase's default `ConfirmationURL`.

## Required secrets

Set these for the Edge Function only. Do not expose them to the Next.js client.

| Secret | Purpose |
| --- | --- |
| `RESEND_API_KEY` | Resend API key used by the Edge Function |
| `SEND_EMAIL_HOOK_SECRET` | Standard Webhooks secret generated by the Supabase Auth Hook |
| `APP_ORIGIN` | Public Lean Excellence Hub origin used in email links |
| `AUTH_EMAIL_FROM` | Sender email address |
| `AUTH_EMAIL_FROM_NAME` | Sender display name |

Example local file: `supabase/functions/.env.example`

Resend initially allows testing with its test sender/domain (for example `onboarding@resend.dev`). Production should use a verified Lean Excellence Hub domain and matching `AUTH_EMAIL_FROM`.

## Local testing

1. Copy `supabase/functions/.env.example` to `supabase/functions/.env`.
2. Generate a local hook secret in Standard Webhooks format, for example `v1,whsec_<base64-secret>`.
3. Uncomment the `[auth.hook.send_email]` block in `supabase/config.toml`.
4. Start Supabase locally.
5. Serve the function:

```bash
supabase functions serve send-email --no-verify-jwt
```

6. Trigger signup confirmation or password recovery from the app.

Normal CI does **not** require a real Resend account. Unit tests mock delivery and signature verification boundaries.

## Hosted deployment sequence

Follow this order exactly. The hook secret is generated in the Dashboard and must be stored on the Edge Function before the hook starts calling it.

### Step 1 — Deploy the Edge Function without JWT verification

From the repository root, linked to the hosted project:

```bash
supabase secrets set \
  RESEND_API_KEY="re_..." \
  APP_ORIGIN="https://your-production-origin.example" \
  AUTH_EMAIL_FROM="auth@your-verified-domain.example" \
  AUTH_EMAIL_FROM_NAME="Lean Excellence Hub"

supabase functions deploy send-email --no-verify-jwt
```

Do **not** set `SEND_EMAIL_HOOK_SECRET` yet. The function is deployed first so you have a stable HTTPS URL for the hook.

Note the deployed function URL:

```text
https://<project-ref>.supabase.co/functions/v1/send-email
```

### Step 2 — Create the Send Email Hook in Supabase Dashboard

1. Open **Authentication → Auth Hooks**.
2. Choose **Send Email**.
3. Hook type: **HTTPS**.
4. URL: `https://<project-ref>.supabase.co/functions/v1/send-email`
5. Click **Generate Secret**.
6. Copy the generated value immediately. This becomes `SEND_EMAIL_HOOK_SECRET`.

The Dashboard generates the secret in Standard Webhooks format, typically:

```text
v1,whsec_<base64-secret>
```

### Step 3 — Store the hook secret on the Edge Function

```bash
supabase secrets set SEND_EMAIL_HOOK_SECRET="v1,whsec_<generated-secret>"
```

This is the chicken-and-egg step: the hook cannot authenticate until the function has the same secret the Dashboard generated in Step 2.

### Step 4 — Create/save the hook

Return to the Dashboard hook form and click **Create Hook** (or save if already open).

### Step 5 — Verify production configuration

Confirm all of the following on hosted Supabase:

- `APP_ORIGIN` matches the public Lean Excellence Hub URL exactly
- `APP_ORIGIN` is present in Auth redirect allow-list settings
- Resend domain/sender is verified for `AUTH_EMAIL_FROM`
- Signup confirmation email CTA opens `/auth/confirm?token_hash=...&type=signup`
- Recovery email CTA opens `/auth/confirm?token_hash=...&type=recovery`

### Step 6 — Smoke test

1. Start a brand-new invitation activation on production.
2. Confirm the email link lands on `/auth/confirm`.
3. Verify the user reaches the invitation continue flow without a second password login.
4. Verify `identity_controls.enrolment_status` becomes `complete` after confirmation.

## Resend setup

1. Create a Resend account and API key.
2. For early testing, use Resend's permitted test sender/domain.
3. For production, verify the Lean Excellence Hub sending domain in Resend.
4. Set `AUTH_EMAIL_FROM` to an address on that verified domain.

## Security notes

- The Edge Function rejects `GET`, unsigned `POST`, invalid signatures, and malformed payloads.
- Do not log `token_hash`, OTP values, invitation tokens, passwords, webhook secrets, or Resend API keys.
- Do not commit real secrets to git.

## Supported email types

Implemented now:

- `signup`
- `recovery`

Structured for extension:

- `invite`
- `magiclink`
- `email_change`
- `email_change_new`

Unsupported action types return hook success without sending email so Auth does not retry indefinitely on types we have not productised yet.
